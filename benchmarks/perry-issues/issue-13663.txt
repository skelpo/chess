## Objective and status

Track the complete measured Perry performance/size investigation as fixable work. **Preserve steady-state performance while reducing binary size. Do not ship the blanket-Oz size preset as a solution.** This tracker distinguishes reproducible compiler/runtime defects from optimization opportunities and remaining attribution work.

Perry 0.5.1663, configured compiler/runtime source `b384cd7be035899e80908c5013baf8e88f08c892`, macOS 26.5 ARM64, Apple M1 Max, 64 GiB. Findings are pinned; latest-main and cross-platform impact still need verification. Related work may already change some paths.

## Baseline: how much extra execution work exists?

Identical engine-only 250,000-node searches (same engine source/budget and matching result fingerprints) retired these median whole-process instruction counts:

| Runtime | Instructions, billions |
| --- | ---: |
| Node 26.5.1 | 18.886 |
| Bun 1.3.14 | 17.898 |
| Perry 0.5.1663 | 105.936 |
| ScriptC 0.4.7 | 16.733 |

Perry executes about **5.6–6.3×** the instructions. This is evidence of excess work per operation; it does not prove that all extra instructions are removable. It excludes TUI rendering as the explanation and predates any size-build changes. Application source is private; these application measurements are context, while the child issues provide complete synthetic public reproductions.

Collector frames appeared on **939 / 35,519 stacks = 2.64%**, an **inclusive stack presence**, not another disjoint self-sample category. Inline/root barriers and bookkeeping are not all counted in that collector figure. Calling this a "GC is only 2.6%" proof would be incorrect.

The `onBoard` specialized entry alone has 7.16% self samples and contains numeric-tag tests, exact conversion, stack/TLS checks and comparison fallbacks. That does not establish 7.16% removable cost: a separate bounds-only micro runs near Node, and simply inlining the helper in the engine did not improve search beyond noise. This negative result is recorded in #13645; do not file a generic bitwise-arithmetic bug from the static assembly alone.

Likewise, generated engine samples include both chess work and inline guards. **The 61.85% generated-code share has not been divided into exact avoidable costs.** #13661 supplies concrete instruction-budget reductions; the remaining full-app attribution is an explicit open task below, rather than being presented as already solved.

## Size accounting and accepted/rejected experiments

Original full executable: **10,267,192 bytes (9.79 MiB)**, including **8,807,472 bytes of machine code**. Largest mutually exclusive code-extent groups from a symbol/address census (aliases counted once, alignment included):

| Retained code group | Bytes |
| --- | ---: |
| Runtime object implementation | 1,815,292 |
| Generated terminal code | 1,083,696 |
| Other libraries/support | 1,021,548 |
| Runtime C ABI helpers | 857,580 |
| GC implementation including barriers | 760,856 |
| Generated engine | 480,020 |
| Node streams | 285,896 |
| Arrays | 231,168 |

These are the largest groups, not the complete total. They are code-size attribution, **not** time attribution or a claim all retained support can be removed. Engine plus TUI comprise ~17.8% of machine code; embedded function source/string sections are only ~110 KiB, duplicate-body estimate ~18 KiB. A 512 KiB dense subclass cache is zero-fill RSS/address-space storage, not 512 KiB of shipped bytes.

The smallest complete experimental executable was **4,647,120 B / 4.43 MiB** but search regressed about **3.1×**. It is rejected for the performance requirement.

A conservative control keeps engine/runtime speed settings and removes size elsewhere: **8,434,960 B / 8.04 MiB**, ~18% smaller, essentially unchanged timings/counts across evaluation, legal moves, perft and search. Validation: 875-assertion native/Node fingerprint, nine CLI scenarios including the 1.5-million-node search, 95 text commands/23 whitespace characters and quit/Ctrl-C/SIGTERM terminal restoration. Original source stays unchanged; experiments use generated copies. This is a single-machine measured result, not a formal zero-regression guarantee.

Intermediate minimal-runtime candidates at 7.43 MiB and 6.23 MiB still regress evaluation (~1.8% and ~4.0%). They are not approved performance-preserving replacements. #13662 contains the controls separating app flags, runtime flags, allocator and loop rewrites.
